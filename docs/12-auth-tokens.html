1. الفكرة في جملة

التوكن زي كرت الغرفة في الفندق. تعطي هويتك (الإيميل وكلمة السر) مرة وحدة في الاستقبال، وياخذ كرت. بعدها تفتح الباب بالكرت بس، وما تعاودش تعطي هويتك.

2. إنشاء الجدول

Sanctum يجي ومعاه ملف الـ migration، لكنه داخل vendor. من Sanctum 4، Laravel ما يشغّلهش من هناك، فلازم تنسخه لمشروعك (publish):

# 1. انسخ الملف لـ database/migrations
php artisan vendor:publish --tag=sanctum-migrations

# 2. شوف شن بيتنفذ بدون ما يتنفذ
php artisan migrate --pretend

# 3. نفّذ (الملفات الجديدة بس)
php artisan migrate

# 4. تأكد: لازم تلقى create_personal_access_tokens_table = Ran
php artisan migrate:status
انتبه: الـ .env يأشّر على داتا بيس السيرفر (عن طريق التانل على port 55000). وmigrate العادي ما يعدّلش جدول users اللي تشغّل من قبل. لو تبي الأعمدة الجديدة (is_active وغيرها) تدخل، لازم migrate:fresh، وهذا يمسح كل البيانات.

موديل User فيه HasApiTokens من قبل، فما تحتاجش تزيد شي ثاني باش يشتغل createToken().

3. أعمدة الجدول

Schema::create('personal_access_tokens', function (Blueprint $table) {
    $table->id();
    $table->morphs('tokenable');                // tokenable_type + tokenable_id
    $table->text('name');                       // 'flutter' أو 'react'
    $table->string('token', 64)->unique();      // sha256 امتاع التوكن، مش التوكن نفسه
    $table->text('abilities')->nullable();      // ["inspector"]
    $table->timestamp('last_used_at')->nullable();
    $table->timestamp('expires_at')->nullable()->index();
    $table->timestamps();
});

nameالاسم اللي تعطيه في createToken()flutter

4. morphs والعلاقة مع users

$table->morphs('tokenable') سطر واحد يعمل عمودين و index:

$table->morphs('tokenable');

// يساوي بالضبط:
$table->string('tokenable_type');
$table->unsignedBigInteger('tokenable_id');
$table->index(['tokenable_type', 'tokenable_id']);

morph معناها "يتشكّل". العمود tokenable_id ما يأشّرش على جدول ثابت، وtokenable_type هو اللي يحدد على أنهي جدول يأشّر. هذا اسمه علاقة Polymorphic.

الشكل 1: كل صف توكن يأشّر على صاحبه بعمودين
  • الصفوف 1 و2 و4 كلهم tokenable_id = 5، لكن 1 و2 لـ Ali، و4 للجهاز، لأن tokenable_type مختلف.
  • Ali عنده توكنين (flutter وreact)، وهذا معناه 1 لـ N.
  • في مشروعنا ما فيش devices، فكل الصفوف بتكون App\Models\User. الجدول الوهمي هذا موجود بس باش تفهم ليش Sanctum عمل عمودين: هو مكتبة عامة، وما يعرفش أنهي موديلات عندك.
العيب: لأن tokenable_id ما يأشّرش على جدول ثابت، الداتا بيس ما تقدرش تعمل FOREIGN KEY. فما فيش cascade، ولو انمسح user تبقى توكناته في الجدول. الحل في القسم 10.

6. abilities (الصلاحيات)

قائمة كلمات على التوكن نفسه، تقول "التوكن هذا يقدر يدير شن". تتخزّن JSON:

$user->createToken('flutter', ['inspector']);   // abilities = ["inspector"]
$user->createToken('test');                    // abilities = ["*"]  يعني كل شي

// الفحص في الكود
if ($request->user()->tokenCan('inspector')) { ... }

// أو في الـ route
Route::post('/visits', [VisitController::class, 'store'])
    ->middleware(['auth:sanctum', 'ability:inspector']);

// تسجيل الـ middleware مرة وحدة في bootstrap/app.php
$middleware->alias([
    'abilities' => \Laravel\Sanctum\Http\Middleware\CheckAbilities::class,     // لازم الكل
    'ability'   => \Laravel\Sanctum\Http\Middleware\CheckForAnyAbility::class, // يكفي واحد
]);
users.roleabilities
مكانهعلى المستخدمعلى التوكن
يتغيّرلما الأدمن يغيّرهثابت لين ينمسح التوكن
يعني"انت مين""التوكن هذا شن يقدر يدير"
مثال: مشرف تعطيه توكن للتقارير بس: createToken('export', ['reports:read']). لو اتسرق، اللي سرقه يقرا التقارير بس، رغم أن صاحبه مشرف.
انتبه: لو غيّرت role المستخدم، توكناته القديمة تبقى بالـ abilities القديمة. امسحها ($user->tokens()->delete())، أو افحص users.role نفسه في middleware. في مشروعنا، فحص role يكفي، وabilities طبقة زيادة.

7. الـ login (مرة وحدة)

  1. التطبيق يبعث الإيميل وكلمة السر لـ POST /login.
  2. Laravel يجيب المستخدم: User::where('email', …)->first().
  3. يفحص بالترتيب: كلمة السر (Hash::check) ← 401، بعدين is_active ← 403، بعدين الـ role يناسب التطبيق ← 403.
  4. createToken('flutter') يولّد نص عشوائي طويل (نسمّوه abc...).
  5. يخزّن الـ hash بس (sha256(abc)) مع User و5، والداتا بيس تعطيه id = 12.
  6. يرجّع 12|abc.... هذي المرة الوحيدة اللي النص الأصلي يطلع فيها. التطبيق يحفظه في secure storage.
$user = User::where('email', $request->email)->first();

if (! $user || ! Hash::check($request->password, $user->password)) {
    return response()->json(['message' => 'Invalid login credentials'], 401);
}
if (! $user->is_active) {
    return response()->json(['message' => 'Account disabled'], 403);
}
if ($user->role !== 'inspector') {                        // login امتاع Flutter
    return response()->json(['message' => 'Not allowed in this app'], 403);
}

$user->tokens()->where('name', 'flutter')->delete();        // جلسة وحدة لكل تطبيق (اختياري)
$token = $user->createToken('flutter', [$user->role])->plainTextToken;
$user->forceFill(['last_login_at' => now()])->save();

8. أي طلب بعد الـ login (يديره auth:sanctum بروحه)

  1. التطبيق يبعث الهيدر Authorization: Bearer 12|abc....
  2. Sanctum يقسم التوكن عند |: الـ id هو 12 والنص هو abc....
  3. يجيب الصف بالـ primary key مباشرة (WHERE id = 12)، فهو سريع وما يدوّرش في كل الجدول.
  4. يحسب sha256(abc) ويقارنه بعمود token. لو مختلف، أو expires_at فات، يرجّع 401.
  5. من نفس الصف يقرا tokenable_type وtokenable_id، فيجيب المستخدم من users. هنا يصير الربط بين الجدولين.
  6. يحدّث last_used_at، ويوصل الطلب للكنترولر.
Route::middleware('auth:sanctum')->get('/me', function (Request $request) {
    $request->user();                          // Ali (من users)
    $request->user()->currentAccessToken();    // الصف 12 (من personal_access_tokens)
});

بعد ما ينمسح الصف، أي طلب بـ 12|abc... يفشل في الخطوة 3 من القسم 8، لأن الصف مش موجود، فيرجّع 401.

الإيقاف (is_active = false): امسح توكناته في نفس اللحظة، وخلّي middleware (EnsureUserIsActive) يفحص is_active مع كل طلب كحماية ثانية.

10. ربط حقيقي بـ cascade (اختياري)

لأن عندنا موديل واحد بس عنده توكنات (User)، تقدر تبدّل morphs بـ FK حقيقي في الملف اللي انعمله publish (مش اللي في vendor):

-   $table->morphs('tokenable');
+   $table->string('tokenable_type');
+   $table->foreignId('tokenable_id')->constrained('users')->cascadeOnDelete();
+   $table->index(['tokenable_type', 'tokenable_id']);
  • tokenable_type لازم يبقى، لأن Sanctum يستعمله في الاستعلام.
  • الآن لو انمسح user، الداتا بيس تمسح توكناته معاه.
  • الملف لازم يجي بعد ملف users في الترتيب. الـ publish يعطيه تاريخ اليوم، فهو بعده.

11. الأمان وأكواد الرد

الكودالمعنىمتى
401"ما نعرفكش"كلمة سر غلط، توكن مش موجود أو انتهى
403"نعرفك، لكن ممنوع"حساب موقوف، role غلط، ability ناقصة
422البيانات ناقصة أو غلطفشل validate()
429محاولات ياسرthrottle على route الـ login
  • الداتا بيس فيها hash التوكن بس، فلو اتسرّبت، التوكنات ما تشتغلش.
  • فحص is_active والـ role يجي بعد كلمة السر، باش ما تكشفش حالة الحساب لحد ما يعرفش كلمة السر.
  • حط ->middleware('throttle:5,1') على الـ login (5 محاولات في الدقيقة).
  • لو تبي التوكنات تنتهي بروحها، حط 'expiration' => 60 * 24 * 30 (بالدقايق) في config/sanctum.php، أو مرّر تاريخ في createToken(..., expiresAt: now()->addDays(30)).
  • في Flutter خزّن التوكن في flutter_secure_storage مش SharedPreferences.
